# #29.0 — Exact Mechanical Execution Eligibility and Trade Authorization

## Status

**LOCKED_CONFIGURATION_REQUIRED** — the gate and fail-closed behavior are locked; realistic price/cost estimates require the runtime models in [[Runtime Configuration Registry]].

## Ownership

Owns the boundary between an armed, mechanically valid setup and an authorized trade. It consumes the frozen theoretical entry from [[#28 Entry-Zone Selection]], immutable stop from [[#13 Stop-Loss Selection]], target from [[#24 LRL Selection]], and the setup-level ≥2R decision from [[#27 Setup Qualification]]. It does not alter setup validity, direction, entry zone, stop, target, or position size.

`SETUP_VALID ≠ ORDER_ALLOWED`

## Two Distinct ≥2R Gates

1. **Setup gate (#27):** uses the theoretical EQ and determines whether the setup may arm.
2. **Execution gate (#29.0):** uses the expected executable entry and determines whether a trade/order may be authorized.

Both must pass. Failure of #29.0 produces `EXECUTION_INELIGIBLE`; it does not rewrite the setup as invalid.

## Required Evaluation Record

`ExecutionEligibilityEvaluation` stores:

- `evaluation_id`, `setup_id`, `evaluated_at`, `direction`
- `theoretical_entry`, `expected_executable_entry`, `expected_entry_method`
- `stop_price`, `target_price`, `spread`, `expected_slippage`, `expected_fees`
- `expected_risk`, `expected_reward`, `expected_executable_r`
- liquidity/available-size evidence when provided, requested quantity, data-quality flags
- `eligibility_state`, reason codes, and immutable source/configuration version IDs

Unavailable information is recorded as `NOT_MEASURED`; it is never fabricated. A mandatory input that is unavailable produces `DATA_ERROR` and no authorization.

## Directional Calculation

After tick normalization and applicable price-based friction:

```text
ExpectedRisk   = abs(ExpectedExecutableEntry - StopPrice)
ExpectedReward = abs(TargetPrice - ExpectedExecutableEntry)
ExpectedExecutableR = ExpectedReward / ExpectedRisk
```

Directional geometry must also hold: long `StopPrice < ExpectedExecutableEntry < TargetPrice`; short `TargetPrice < ExpectedExecutableEntry < StopPrice`. Fees that the configured model expresses in R must reduce executable reward consistently and must not be double-counted by [[#29.5 Execution Costs]].

Authorization requires `ExpectedRisk > 0` and `ExpectedExecutableR ≥ 2.0`. A stricter configured or existing rule prevails. The selected target may not be moved farther away to manufacture eligibility.

## Execution State Machine

```text
SETUP_VALIDATED → EXECUTION_EVALUATING
EXECUTION_EVALUATING → EXECUTION_ELIGIBLE | EXECUTION_INELIGIBLE | DATA_ERROR
EXECUTION_ELIGIBLE → TRADE_AUTHORIZED | AUTHORIZATION_REVOKED
TRADE_AUTHORIZED → ORDER_PENDING
ORDER_PENDING → ORDER_WORKING | ORDER_REJECTED | ORDER_CANCELED | ORDER_EXPIRED
ORDER_WORKING → PARTIALLY_FILLED | FILLED | ORDER_CANCELED | ORDER_EXPIRED
PARTIALLY_FILLED → FILLED | ORDER_CANCELED | ORDER_EXPIRED | RECONCILIATION_REQUIRED
FILLED → POSITION_OPEN
POSITION_OPEN → POSITION_MANAGING → EXIT_PENDING → CLOSED
```

`SETUP_INVALID`, `EXECUTION_INELIGIBLE`, `DATA_ERROR`, `ORDER_REJECTED`, `ORDER_CANCELED`, `ORDER_EXPIRED`, `UNFILLED`, `CLOSED`, and `RECONCILIATION_REQUIRED` are terminal for the affected evaluation/order attempt unless a new immutable evaluation or replacement order is created. History is appended, never overwritten.

## Guards and Ownership

- #27 owns `SETUP_VALIDATED`; #29.0 owns evaluation, eligibility, authorization, and revocation.
- [[#29.1 Entry Execution]] owns order states and entry fills.
- [[#29.6 Position Lifecycle]] owns position states after fill.
- [[#29.4 Exit Resolution]] owns exit resolution and exit-pending completion.
- Material change to expected entry, spread, slippage, available size, stop, target, or costs before submission requires a new evaluation.
- If eligibility disappears before submission: revoke authorization; submit no order.
- If it disappears while an unfilled order works: cancel the order. Partial exposure is managed by #29.6 and may not be erased.
- Repeated events are idempotent by immutable ID and current state; prohibited transitions emit no state mutation and require an audit record.

## Hard Invariants

- no valid setup automatically creates a trade or order
- no order without a current eligible evaluation and authorization
- realistic executable entry, not theoretical EQ, owns the authorization-time ≥2R test
- actual fills never retroactively change theoretical or expected values
- source-specific concepts excluded by [[Polymarket Bot Execution and Inventory Management Analysis]] have no authority in the core engine
