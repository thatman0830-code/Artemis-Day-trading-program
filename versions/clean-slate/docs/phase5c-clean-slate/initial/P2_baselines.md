# P2 — Baseline methodology (initial first draft)

**Date:** 2026-09-24  
**Role:** P2, baseline methodology  
**Status:** Independent initial draft; prospective methodology only  
**Independence:** Prepared independently from the technical inventory alone. I did not consult other agents' drafts, historical protocols, proposals, reviews, evaluation outputs, model outputs, protected data, or protected outcomes. No model or data was run or inspected.

## Scope and known technical identity

The sole project source consulted was `docs/BOT2_PHASE5C_TECHNICAL_INVENTORY.md`. It identifies instruments ES and NQ; target horizons 5, 15, and 30 minutes; and three separate three-class targets: direction (DOWN/FLAT/UP), volatility (LOW/NORMAL/HIGH), and structure (RANGE/TRANSITION/TREND). It lists WF1–WF4 identifiers but does not specify their dates, split semantics, or eligibility. It also records 24 features, sequence length 8, and several existing A0 implementation names. Those names are code identities, not adopted scientific methods or evidence of validity.

This draft proposes *forecast-classification* baselines. It does not define a trading strategy, portfolio, performance metric, split, or score. Every baseline is to be instantiated separately for each instrument, horizon, and target head. A model must never pool ES and NQ labels into one fit. The canonical class orders for deterministic tie-breaking are the orders shown above.

## Shared point-in-time rules (prospective choices)

1. At each forecast origin, inputs must have been available to the forecasting system by that origin. The target for an origin is not available merely because its row exists: a prior target can be used as a predictor only after its full target horizon has elapsed and its label is finalized. The inventory does not establish the origin timestamp, label-finalization rule, feature availability timestamps, or target maturity metadata. Those are prerequisites to define before evaluation. If they cannot be established, label-history baselines are ineligible; do not substitute a later-known label.
2. Fit-only quantities (class counts, transition counts, imputations, feature means/scales, and coefficients) use only the designated training observations whose labels would have been available by the applicable fit time. Test labels never affect a prediction. A rolling update is permissible only if a future evaluation protocol explicitly declares it and admits only labels matured by each refit time; otherwise use the fixed training window.
3. Baseline predictions are hard class predictions. Where a method has a probability distribution, retain it as a secondary output only if the evaluation specification requests probabilities. Choose the class with greatest probability/count; exact ties resolve to the first class in that target's canonical order. No stochastic sampling is used.
4. A prediction is eligible only where the target row and required point-in-time inputs exist and pass the same ex-ante data-quality rules for every compared method. Method-specific inability to predict is recorded as abstention with its reason and coverage; it must not silently remove that row from another method's denominator. If an all-method comparison requires a common cohort, define that cohort before observing results.
5. Missing or non-finite inputs do not trigger a fallback prediction. A history-dependent method abstains if its required matured history is missing. A fitted method abstains if fit prerequisites fail. Do not back off from an unavailable transition prediction to majority or another family without separately naming and evaluating that hybrid.

These are prospective design choices, not technical properties established by the inventory. Forecast evaluation literature describes forecast origins, fixed versus rolling origins, and the value of multiple out-of-sample periods; a future protocol must specify these elements and preserve point-in-time availability for the chosen design.[Tashman (2000)](https://doi.org/10.1016/S0169-2070(00)00065-0), [Cerqueira, Torgo & Mozetič (2022)](https://pmc.ncbi.nlm.nih.gov/articles/PMC9718476/)

## Baseline families

| Family | Adopt? | Definition and information at prediction origin | Training / eligibility / abstention |
|---|---|---|---|
| **Empirical prior / train majority** | Yes; primary constant-class reference | For each instrument × horizon × target head, count each class in eligible training labels and predict the most frequent. The associated empirical class-frequency vector may be retained as a prior-probability output. This is the categorical counterpart of a training-only historical-average reference; it is not a forecast from test-period class frequencies. | Requires at least one eligible training label and a well-defined class mapping. If training counts tie, apply the canonical order. If no eligible training labels, abstain. Do not rebalance classes or use test prevalence. Fit once per authorized fit time. |
| **Persistence / previous matured label** | Yes; conditional on label-maturity metadata | Predict the most recent finalized label for the same instrument × horizon × head. “Previous” means latest label actually known by this origin, not necessarily the immediately preceding row or decision bar. | Requires a previous valid, matured target label. Reset at a new session and contract; do not bridge either boundary. If the label’s maturity time, session, or contract cannot be verified, abstain. No fallback. |
| **First-order transition baseline** | Yes; conditional on label-maturity metadata | Within the current instrument × horizon × head, estimate a 3×3 transition table from consecutive valid matured labels. At origin, condition on the latest matured prior label and predict the destination class with the largest training-only transition count in that row. Counts may be normalized to probabilities; normalization does not change the selected class. | Count pairs only when both labels are finalized and available in the fit data, in temporal order, with no gap, session boundary, or contract boundary between them. Use unsmoothed empirical counts as the transparent primary definition. If the conditioning state has no observed outgoing transition, abstain; do not back off. Resolve ties by canonical class order. The empirical transition matrix is the standard count-based estimator for a finite-state Markov chain; this benchmark does not assert the market is Markovian.[Anderson & Goodman (1957)](https://doi.org/10.1214/aoms/1177707039) |
| **Zero / no-change reference** | Conditional adoption: direction only, subject to semantic validation | Predict FLAT at every origin for the direction head. This is a class-label reference, not a numerical zero-return forecast. Adopt it only if the authoritative target definition confirms FLAT denotes a no-directional-change band that makes this interpretation meaningful. | Requires only the target class mapping, not fitted data. If FLAT's target semantics cannot be verified from the evaluation-authorized target specification, mark this candidate unresolved/ineligible. Do not invent a neutral class for volatility or structure: their listed classes have no explicit no-change state. No zero baseline is proposed for those heads. |
| **Simple linear classifier: multinomial logistic regression** | Yes; secondary learned reference | Fit one plain multinomial logistic classifier per instrument × horizon × head, using the declared 8×24 feature history (flattened to 192 values in sequence order) available at origin. Use a fixed, predeclared L2 penalty, intercept, no class weighting, no feature selection, and no validation-based tuning. A standard multinomial logistic model estimates class probabilities with a softmax link; it is a linear decision-boundary benchmark, not a neural-network analogue.[Scikit-learn LogisticRegression documentation](https://scikit-learn.org/stable/modules/generated/sklearn.linear_model.LogisticRegression.html) | Require a declared training set, at least two observed target classes, and enough eligible rows for a numerically successful fit. Keep the full canonical class space; a class absent from training has no learned support and must be disclosed. Any preprocessing is fit on training rows only: standardize each feature using training mean and scale; set a zero-variance standardized column to zero. If missing values are allowed, use training-only column means for imputation and abstain when a column has no observed training value; do not inspect test distribution to preprocess. Use a fixed deterministic solver/settings and tie-break by canonical class order. If the fit fails or required input is unavailable, abstain. |

The usual univariate naïve forecast carries forward the most recent observation and simple historical references are widely used as benchmarks; the categorical persistence and constant-class adaptations above are explicit proposed analogues, not claims that numeric forecast methods transfer unchanged.[Hyndman & Athanasopoulos, *Forecasting: Principles and Practice*, “Some simple forecasting methods”](https://otexts.com/fpp2/simple-methods.html)

## Sessions, contracts, and instrument pooling

The inventory lists six ES and six NQ contracts and notes `session_id` and `contract_id` as declared raw-event schema fields, but it does not specify their availability on a target row, session calendar, roll construction, or whether feature and target definitions are comparable across contracts. The following are conservative prospective defaults:

- Never pool instruments. Estimate all training-based baselines separately for ES and NQ.
- Do not carry persistence or transition state across session or contract boundaries. Require reliable session and contract identity at both origins and labels for these baselines; otherwise abstain.
- For prior and logistic fits, keep contract strata separate by default. Pooling multiple contracts within one instrument is eligible only after a protocol establishes common feature/target semantics, stable contract mapping, and absence of roll leakage. Do not assume those properties from the symbol list.
- Fit and score every family for each of the 5/15/30-minute horizons and each target head independently. Never use a label from another horizon or head as if it were the matching target.

These decisions may reduce eligibility around contract starts, session boundaries, or sparse histories. That is a methodological limitation to report, not a reason to infer outcomes or relax point-in-time controls after results are seen.

## Portfolio treatment

No baseline portfolio is adopted. The declared experiment object is a future-state classification problem, and the inventory supplies no action mapping, position sizing, transaction-cost, execution, capital, or risk specification. Turning DOWN/FLAT/UP into short/flat/long positions would add an unsupported strategy assumption; volatility and structure classes have no direct action mapping at all. If a later authorized protocol separately asks for portfolio analysis, it should define one fixed mapping and all costs/execution assumptions before evaluation and apply the identical mapping to every forecast method. That would be a distinct prospective experiment, not part of these forecast baselines.

## Technical constraints vs. unresolved protocol choices

**Recorded technical constraints:** declared classes, instruments, horizons, feature-row identity/shape, listed contract symbols, walk-forward IDs, and the fact that the inventory itself leaves split dates/semantics/eligibility unspecified.

**Prospective choices in this draft:** distinct per-head/per-horizon/per-instrument fits; canonical tie order; matured-label rule; session/contract resets; unsmoothed transition counts with abstention on unseen rows; no-change benchmark limited to direction conditional on FLAT semantics; fixed L2 multinomial logistic recipe; and no portfolio layer.

**Must be resolved before an evaluation can use these definitions:** forecast-origin and feature-availability timestamps; target-label finalization/maturity timestamps; training/validation/test membership and any rolling refit schedule; session and active-contract mapping at each target row; contract comparability/roll policy for any pooled fit; authoritative meaning of FLAT; permitted treatment of missing features; software/version and fixed solver settings for logistic regression; and the method-specific/common-cohort reporting rules. WF1–WF4 names alone resolve none of these.
